# 假阳性闸门

报告前逐项核对；命中任一条即不按已确认漏洞报告。

## 输入可控性

- 只来自部署配置、环境变量、常量、运维后台或可信内部服务的值，不视为攻击者可控。
- 请求参数、请求头、Cookie、路径段、上传文件内容/文件名、WebSocket 消息、队列消息、反序列化数据才视为不可信输入。
- 来自数据库的值只有在“其他用户可写入且当前用户可读”时才按不可信处理，并说明依据。
- 不能确认输入来源时，不报高严重级，置信度最多 `medium`。

## 框架与上游保护

- ORM/预编译参数、模板自动转义（Django/React/Vue 等）、CSRF 中间件、统一鉴权中间件、输出编码器：先确认当前调用确实经过它们；绕过写法（`raw`/`extra`/`|safe`/`dangerouslySetInnerHTML`/`v-html`）才按漏洞处理。
- 上游已有白名单、类型/范围校验、路径规范化时，检查当前 sink 是否仍可被绕过；仅“缺少第二层防御”不算漏洞。
- 框架默认安全行为（自动转义、参数化）不能当作已经确认；以片段中的实际用法为准。

## 代码形态

- 测试、示例、fixture、文档字符串、注释、死代码默认不报，除非它们进入生产构建或运行时。
- 常量拼接（无变量）不构成注入；`eval` 只接受常量时按代码质量记录，不按 RCE 报告。
- 需要已认证/管理员权限才能到达的路径：把它写成前提条件，不声称未授权可利用。

## 不确定性

- 未提供上游调用链、路由注册、部署配置时，不得假设“没有校验”，也不得假设“一定可达”。
- 无法闭环的候选：不报，或降为 `info` + `low`，并在 `detail` 标明缺失的上下文。
- 不得为了凑数把同一根因拆成多条，也不得把“建议加固”写成漏洞。
